# Architecture Benchmark

## Scope

Both candidates consume the same deterministically generated synthetic invoice images and the same OCR-box ground truth:

- `ruled-invoice.png`: 8 × 6 grid with explicit blank cells;
- `borderless-invoice.png`: 7 × 6 aligned text table with an empty quantity cell;
- `skewed-invoice.png`: the ruled invoice rotated 3.2° on a larger page.

The geometry benchmark intentionally holds OCR text/boxes constant so it measures table detection, row/column recovery, cell placement and blank materialization rather than conflating those results with OCR recognition quality. RapidOCR is measured separately through `/api/self-test` and deployed invoice tests.

## Candidate A

**Browser OpenCV.js geometry + Vercel RapidOCR.**

The benchmark page uses the actual production `public/opencv-worker.js`, one lazy worker/OpenCV instance, transferable `ImageBitmap`s and the production-equivalent OCR-box borderless fallback. It records:

- first/cold worker run and warm run;
- image bytes;
- row, column, cell-count, placement and blank-cell accuracy;
- maximum main-thread timer lag;
- JavaScript heap delta when Chromium exposes it;
- worker diagnostics and Mat cleanup count.

Result file: `benchmarks/results/candidate-a.json` generated by `npm run benchmark:browser` in CI.

## Candidate B

**Python OpenCV geometry + the same OCR boxes.**

The independent benchmark implementation lives under `experiments/`; it is deliberately not imported by the production API.

Local benchmark on Python 3.13.5 / OpenCV 4.13 produced:

| Fixture | First run | Warm median | Row | Column | Cells | Placement | Blank cells |
|---|---:|---:|---:|---:|---:|---:|---:|
| Borderless | 60.62 ms | 44.85 ms | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| Ruled | 60.88 ms | 57.60 ms | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| Skewed | 85.30 ms | 84.99 ms | 1.000 | 1.000 | 1.000 | n/a | 1.000 |

Measured peak RSS increase for the geometry process: approximately 36.4 MB. These values describe only the small synthetic structural spike, not the RapidOCR model cold start or arbitrary real invoices.

Machine-readable result: `benchmarks/results/candidate-b.json`.

## Metrics not fabricated

The following require a deployed function or manual desktop application and are therefore reported only when actually executed:

- Vercel build/function bundle size;
- deployed RapidOCR cold and warm request time;
- deployed function peak memory;
- Microsoft Excel open result;
- LibreOffice headless open/save result;
- Google Sheets import result;
- OCR reading accuracy on the user's real invoice set.

CI validates workbook structure by loading the ExcelJS output again. A compatibility script then checks a generated workbook with `openpyxl` and LibreOffice when available. Google Sheets remains a documented manual gate because this repository has no Google Drive authorization.

## Decision rule and current selection

Candidate B proves that server OpenCV can reconstruct this controlled set accurately, but it would add Python geometry work and OpenCV memory/cold time to every OCR invocation. Candidate A uses the same structural approach in a background Web Worker, keeps the Python response JSON-only, and avoids packaging a second permanent pipeline.

**Selected V1 architecture: Candidate A**, provided the CI browser benchmark maintains comparable structural accuracy and acceptable main-thread lag. Candidate B stays as the benchmark/fallback experiment only. If Candidate A fails those gates, this document must be updated and the production choice revisited rather than silently maintaining both pipelines.

## Minimum acceptance gates

- mean row, column and cell-count accuracy ≥ 0.90 on the locked generated spike fixtures;
- blank-cell accuracy = 1.00 on the locked generated fixtures;
- cell-placement accuracy ≥ 0.95 where OCR-box ground truth exists;
- max browser main-thread lag below 150 ms on CI Chromium;
- no unreleased `cv.Mat` paths in the worker;
- processed upload target ≤ 3.2 MB and server hard limit ≤ 3.6 MB;
- XLSX contains every table plus Raw OCR, Unassigned OCR and Diagnostics sheets.

Real invoice accuracy must be added before calling the system generally reliable. If neither candidate meets the same thresholds on the supplied real invoice set, stop and report rather than adding a third permanent pipeline.
